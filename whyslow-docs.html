WhySlow

Open the window, press one button, get a plain-language answer instead of a graph.

WhySlow is written for someone who does not read the built-in Profiler. Every screen states a finding in a sentence, says why it matters, and offers a Fix where the fix is safe and reversible. Where a fix is not safe, it says so and leaves the decision to you.

Window → WhySlow.

The five tabs

Each tab answers one question. If you know your question, you know your tab.

Checkup — "is this scene set up sensibly?"

Static analysis of the open scene and of your scripts. No Play Mode, no build.

  • Scene runs around thirty-five checks over lights, shadows, cameras, canvases, physics, animation and project settings, scores them, and highlights flagged objects in the Scene view. Fixes that are safe to apply in bulk are collected behind one button.
  • Code scans your scripts for allocation patterns in code that runs often — string building, LINQ, GetComponent, Camera.main, allocating physics queries, Debug.Log, and more — with no Play Mode required. It reads a project you have just opened.

Two things keep that scan honest. A finding behind an early return or a cache is marked Guarded rather than presented as certain, and code inside #if UNITY_EDITOR, DEVELOPMENT_BUILD or ENABLE_DEBUG is not reported at all, because it never reaches a player build.

Project Assets — "what has piled up in here?"

Three audits of what is on disk. None of them needs a build.

  • Dead Assets finds assets nothing can reach, grouped by folder. See below.
  • Duplicates finds byte-identical files and materials that differ in nothing that matters.
  • Import Settings finds assets spending memory on data nothing uses. On meshes: rig and blend shape data on models that have neither, Read/Write keeping a second copy in CPU memory, and Humanoid rigs that are not being retargeted. On textures: mipmaps on sprites drawn at a fixed size, Read/Write, and textures that will be built uncompressed. On audio: a Load Type that contradicts the clip's size, sample rates above what a phone can use, multichannel clips that will be flattened anyway if played positionally, and clips authored from an already-lossy file. Plus animation clips animating scale.

Two of those never batch. Forcing a clip to mono is audible, and whether it is played positionally cannot be seen from a scan; a lossy source has no fix at all, because the remedy is re-exporting the file. The texture fix turns compression on and leaves the format Automatic, so Unity picks per platform -- which compressed format is right depends on the oldest device you support, and that is your decision, not the tool's.

Build X-Ray — "why is my build this big?"

Needs a captured build; WhySlow records one automatically every time you build.

Overview shows a treemap and a ranked table of what took the space, with reversible importer fixes and an estimate of what each saves. Build Diff compares two builds per asset and names the biggest contributor to any growth.

Performance Hunter — "why does it stutter while playing?"

Play Mode measurement. Start a hunt, play the part that feels bad, and watch allocations accumulate by call site, with the worst frames kept alongside what caused them. It also diagnoses what the garbage collector actually cost, from its own profiler samples rather than an assumed budget, and reports what the renderer is being asked to draw.

A call site is named as an offender only when it is currently allocating or recurs in at least a tenth of scanned frames. A rare event with a large total is a measurement, not a problem, and is counted without being blamed.

Compile Time — "why is my day slow?"

Not about your game: about the wait between saving a script and being able to play again.

It prices each assembly by what has to rebuild when you touch it, using durations measured from your own compilations. It reports reference rings in full, references your asmdefs declare that nothing uses, editor assemblies referenced from runtime ones, and both structural extremes — a monolithic Assembly-CSharp and a project split so far that fixed overhead dominates.

Timings only appear for assemblies observed compiling alone, because a round shared by several assemblies cannot be divided between them without guessing.

Quarantine is not deletion

Dead Assets never deletes anything. When you move assets to quarantine:

  1. A backup .unitypackage is exported first.
  2. Each file's contents and its .meta are hashed.
  3. Both files are moved out of Assets into a WhySlow_StrippedAssets folder beside your project, one folder per run.
  4. A manifest.json recording the original paths and hashes is written next to them.

Unity then behaves as though the files were gone, which is exactly how you find out whether anything needed them. Restore puts every file back at its original path and verifies its hash; if anything no longer matches, it says so rather than pretending the restore was clean.

Commit to version control first anyway. Not because the operation is reckless, but because a known-good point costs you nothing and answers every later doubt.

What is never reported as dead

Trust in this list is worth more than completeness, so whole categories are excluded even though nothing references them:

  • Scripts, assemblies and asmdefs.
  • Documentation and licences — .txt, .md, .pdf and friends. They do not ship, they cost nothing, and having no references is what documentation is.
  • Native libraries and build inputs — .aar, .jar, .so, .dylib, .pom, .gradle, and anything inside a .framework, .androidlib or .bundle. Gradle and Xcode consume these; the asset graph never points at them.
  • Build configuration by name, anywhere — link.xml, google-services.json, GoogleService-Info.plist, AndroidManifest.xml, NuGet.config and similar. Unity and the platform toolchains find these by name. Removing link.xml breaks only release builds, which is the worst way to learn about a mistake.
  • Shader authoring sources — .cginc, .hlsl, .glslinc and Shader Graph sub-graphs. Shaders pull these in at import time, which leaves no reference for the asset graph to follow.
  • Everything under Resources, StreamingAssets, Editor, Gizmos, Plugins and Editor Default Resources, every scene listed in Build Settings — ticked or not — and everything those scenes reference, every asset referenced from project settings, from a quality level's render pipeline asset, or registered in Build Settings by a package such as the Input System or Localization, everything carrying an AssetBundle name, every registered Addressables entry, and the Addressables configuration itself.

Scenes that are in Build Settings but unticked count as roots deliberately. Unticking a level while you work on another is normal; having the tool offer to quarantine it while you do is not.

Before it lists anything, the scan states how many roots it protected and how many Addressables entries it found. If that number is zero in a project that plainly uses Addressables, treat the list with suspicion and tell me — it means detection failed, not that your content is dead.

What it cannot see

  • Assets loaded by a name assembled at runtime. A path built from pieces, or an Addressables address held in data, is invisible to a reference graph.
  • Types resolved by reflection. An unused asmdef reference used only through Type.GetType looks unused, which is why removing a reference is offered as an easily reversed experiment rather than a certainty.
  • Coupling inside method bodies. The monolith split ranking reads type signatures only, so it is a place to start looking, not a list of safe extractions.
  • Whether a scene is slow on a device. Everything measured in Play Mode is measured in the editor, on your machine. Counts — draw calls, batches, allocations — carry over. Milliseconds do not.

Where a check knows it might be wrong, it says so on the finding instead of in a footnote.

Ignoring things

Every list can be told to stay quiet: a folder or a single file in Dead Assets, an asset in Import Settings, an assembly in Compile Time. Dismissals persist between runs and are stored per project in Library, so they are yours and not your team's.

Options in the window header shows how much has been silenced in each tab, with one item to clear all of it. That count is there on purpose: a tool told to ignore enough things stops finding anything, and nothing else would show you why. The same menu offers Share report, which writes a one-page PNG summary of what you have measured and fixed.

Preferences

Edit ▸ Preferences ▸ WhySlow holds two things.

Import Watcher notices assets as they are imported and warns about an uncompressed texture, a raw PCM clip or an unexpectedly heavy mesh at the moment it enters the project, rather than after a build. Each category can be switched off.

Import backups lists what the import fixes changed, most recent first, with a Restore for each. Every fix records the importer's complete settings before it writes anything, so Restore puts back exactly what was there.

Both live in Library/WhySlow, which means they are per project, per machine, and not shared with your team. It also means a deleted Library takes the backup history with it — Restore is for undoing a fix you just made, not an archive.

Promises

  • Editor-only. The assembly is Editor-platform only. Zero bytes reach your player build.
  • Nothing changes without a click. No project setting, importer or asset is touched until you press a button that says so.
  • Every fix is reversible. Scene and project changes go through Undo; importer changes are backed up before they are written and can be restored per asset or per operation; quarantine is a move with a manifest and a verified restore.
  • No dependencies. UnityEngine, UnityEditor and Unity.Profiling. No NuGet, no DLLs, no third-party packages.

Requirements

Unity 2021.3 LTS or newer. Verified on Unity 6 and 2022.3.
